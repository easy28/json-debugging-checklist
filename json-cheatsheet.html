The JSON Escape & Encoding Cheat Sheet

The string escapes that actually exist, the numbers that lie to you, the invisible characters that break parsers, and the real differences between JSON, JSON5, JSONC and NDJSON. Every tool recommended below is 100% client-side — nothing you paste ever leaves your browser.

1 · The complete JSON escape table

JSON strings allow exactly eight escape forms. Anything else starting with \ is invalid — a surprisingly common cause of validator errors after hand-editing config files.

Test any escape sequence round-trip with the JSON escape tool (minimal or ASCII-safe \uXXXX mode) and JSON unescape (which validates the result instead of silently returning garbage).

2 · Unicode: surrogate pairs and invisible characters

  • Astral characters need two escapes. \uXXXX covers one UTF-16 code unit, so 𝄞 (U+1D11E) is \uD834\uDD1E — a surrogate pair. A lone surrogate such as \uD834 alone is invalid JSON and some parsers accept it silently, only to crash later.
  • The PDF/Word copy trap. Documents convert hyphens and quotes to typographic ones (U+2010, U+201C) and spaces to \u00A0 — all perfectly printable but structurally fatal when pasted as code. They're invisible in most editors; a tree viewer that shows raw escapes makes them obvious (try the JSON viewer).
  • U+2028 / U+2029. These line/paragraph separators are valid inside JSON strings, but before ES2019 JavaScript source code rejected them — old bundlers and templates can still choke on logs containing them.
  • The BOM. RFC 8259 says producers MUST NOT add a UTF-8 BOM and parsers MAY ignore it — so plenty of parsers don't. A file that "looks fine" in an editor but fails with Unexpected token ﻿ is almost always a BOM. Re-save without it.

4 · The JSON-in-JSON double-escape

The most confusing sight in debugging: a value that looks like "{\"a\": 1}". That's a JSON document serialized as a string inside another JSON document — logs, webhooks and message queues do this constantly. Strip one level of escaping and re-parse. Two signs you're looking at it: backslashes before every quote, and a validator that parses the envelope fine but the payload is one opaque string. The unescape tool performs exactly this peeling and validates what's underneath; for nested payloads use jq in the browser (.payload | fromjson) as described in running real jq client-side.

6 · Base64 inside JSON

Binary payloads (images, crypto, PDFs) travel inside JSON as base64 strings. Three things bite people:

  • Two alphabets. Standard base64 uses + and /; the URL-safe variant (JWTs, query params) uses - and _ and usually drops the = padding. Mixing them fails decode with a confusing "invalid character".
  • Size. Base64 inflates payloads by ~33% — for large blobs it's often the reason an API suddenly hits a body-size limit. Minify the JSON envelope first with the minifier (it reports real gzip savings, not just byte counts).
  • Padding and MIME newlines. Pasted PEM-style blocks contain line breaks that strict decoders reject. A decoder that tolerates both is described in base64 decoder robustness; round-trip either direction with JSON→Base64 and Base64→JSON.

7 · Schemas: catching all of the above before runtime

Escape tables and number ranges are exactly the kind of contracts a JSON Schema expresses: pattern for strings, maximum / multipleOf for numbers, format for base64. Generate a first draft from a sample with the schema generator, then validate incoming payloads with the AJV-based validator — the workflow is walked through in how to validate JSON against a schema and generating draft-2020-12 schemas from examples.
